# アーキテクチャ決定記録

## Goのバージョンとコードの配置

**状態:** 採用

IchnographはGoで実装します。最低Goバージョンは、Goプロジェクトがサポートする最も古いリリース系列に合わせます。2026年11月5日時点ではGo 1.26です。公式サポートの変更に合わせて最低バージョンを見直します。開発とビルドにはサポート対象のパッチリリースを使います。[Goのリリースポリシー](https://go.dev/doc/devel/release)を参照してください。

コマンドのエントリーポイントは`cmd/`に置き、実装は`internal/`配下で機能ごとのパッケージにまとめます。eBPF関連の機能は`internal/ebpf`から始めます。internalパッケージはモジュール内で再利用できますが、公開ライブラリのAPIではありません。責務が明確になった段階でパッケージを追加します。

## 実行時の根拠の収集

**状態:** 方向性を採用。イベントの選定と実装は検証が必要

LinuxではeBPFを使って実行時の根拠を収集し、[プロダクト要求](prd.ja.md)に従ってファイルアクセスから始めます。収集処理をコマンドのエントリーポイントから分離し、必要に応じて実行ファイル、デバッグ情報、パッケージ情報などを使ってGo側で観測結果を補足します。ネイティブ連携に必要な場合はcgoを使用でき、そのビルドへの影響を文書化します。

ディスクリプタの読み書きを逐一記録するのではなく、依存関係の根拠に必要なイベントを選びます。ファイルアクセスと関連するディスクリプタの使用の根拠を保持しながら、設計の検証に応じて現在の詳細なディスクリプタイベント収集を置き換えるか削除します。イベントの削除前に、継承されたディスクリプタやファイルを伴うメモリマッピングなどのアクセス経路を評価します。ディスクリプタの内容や通信ペイロードは収集目的に含めません。ネットワークの対応付けは将来の機能であり、現在の対応範囲を示すものではありません。

実際のワークロードに対応し、資源の使用量を抑えられるよう設計します。損失と収集エラーを明示し、可能な範囲で原因を区別します。変更の有効性を判断する前に、代表的なワークロードでイベントの選定と損失の状況を検証します。具体的なプローブ、イベント表現、バッファリング、対応カーネル、必要な権限は実装時に決定します。既存の収集処理は変更されるまで、この方向性と異なる場合があります。
