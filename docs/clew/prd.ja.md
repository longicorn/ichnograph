# プロダクト要求: clewサブコマンド

[English](prd.md)

## 目的

`ichnograph clew`サブコマンドは、特権不要の後処理エントリーポイントとして、`ichnograph trace`が出力した生JSONログをより扱いやすい構造化表現へ変換します。[ichnograph全体のプロダクト要求](../prd.ja.md)において、`clew`は[trace](../trace/prd.ja.md)によるカーネルレベルの生観測ログと、より高水準な実行時情報の正規化・外部メタデータ統合との橋渡しを担います。

`clew`はコンポーザブルなパイプラインとして設計されており、ある`clew`実行の出力を後続の`clew`実行の入力として再度渡し、必要に応じて外部メタデータと組み合わせることで、観測情報を段階的にフィルタリング・拡充・正規化・マージできます。生トレースレコードを`pid`と`tid`でグルーピングする機能に加え、共通のフィールド／値比較述語によるフィルタリング（`include` / `exclude`）、ユーザー指定の条件付きタグ付け、およびファイル内容に基づく種別タグ付けをサポートします。追加の拡充処理や外部メタデータのマージ機能は、開発の進展に合わせてCLIオプションとして段階的に定義・追加します。

## コマンドラインインターフェース

```sh
ichnograph clew [-group-by pid,tid] [-include <predicate>...] [-exclude <predicate>...] [-tag <tag>:<predicate>...] [-tag-file-type] [-o output.json] [input.json]
```

- **`input.json`（任意）**: 入力JSONファイルのパス。省略時または`-`の場合は標準入力（`stdin`）から読み込みます。
- **`-o <path>`（任意）**: 出力JSONファイルのパス。省略時または`-`の場合は標準出力（`stdout`）へ書き出します。
- **`-group-by <keys>`（任意、デフォルト: `pid,tid`）**: 入力レコードのグルーピング方式。初期状態では`pid,tid`をサポートします。
- **`-include <predicate>` / `-exclude <predicate>`（任意、複数指定可）**: 共通のフィールド／値比較述語モデルを用いてレコードを絞り込みます（例: `success=true` / `success=false`のような完全一致や、`path`・`resolved_path`等に対する部分文字列一致／パターン一致）。
- **`-tag <tag>:<predicate>`（任意、複数指定可）**: 述語に一致したレコードへユーザー指定のタグを付与します（例: `.rb`のパスに`ruby`を付与）。構文は完全一致が`<tag>:<field>=<value>`、部分文字列一致が`<tag>:<field>~=<value>`です。フィールド名とタグ名は英字またはアンダースコアで始まり、英数字とアンダースコアのみを使用できます。値は空にできません。
- **`-tag-file-type`（任意）**: 組み込みプリセットおよびローカルファイルの内容検査（ELFやshebangスクリプト等のファイルヘッダ／マジックバイト判定、および必要に応じた外部`file`コマンド連携等）によりファイル種別を判定し、対応するタグ（`elf`、`ruby`等）を付与します。
- 今後の加工・情報拡充・外部メタデータマージ機能は、サブコマンドを分割せず`clew`のオプションとして追加します。
- 終了ステータス:
  - `0`: 処理および出力が成功した場合。
  - `2`: CLI引数、オプション値、または述語式が不正な場合（標準エラー出力にusageを表示）。
  - `1`: 入力の読み込み、JSONパース、入力構造の検証、または出力の書き込みに失敗した場合（標準エラー出力にエラーを表示）。

## 入力とパイプライン契約

- `ichnograph trace`の生JSON出力（トップレベルの`records`配列および完全性メタデータを含む）と、`clew`の出力JSON（`format: "ichnograph.clew.v1"`のようなトップレベルのフォーマット/スキーマ識別子で判別）の双方を入力として受け入れます。
- 生`trace` JSON入力と`ichnograph.clew.v1` JSON入力の双方に対して、同一のフィルタリングおよびタグ付け仕様を適用します。
- パイプラインの各段階が後続処理を壊さずに情報を引き継ぎ・段階的拡充できるよう、未知のフィールドや拡張フィールドは可能な範囲で保持します。
- すべての処理は特権不要で動作します。入力JSONのみに依存する処理は同一入力に対して決定的に動作し、ローカルファイルの内容検査を伴う種別判定は後処理時点のローカルファイルシステム状態に依存します。

## フィルタリングおよびタグ付けの仕様

- **共通の比較述語モデル**: フィルタリング（`-include`、`-exclude`）と条件付きタグ付け（`-tag`）は、レコードの任意トップレベルフィールド（`success`、`path`、`resolved_path`、`event`等）を対象とする共通の述語評価モデルを共有します。述語は完全一致（真偽値・数値・文字列）および部分文字列一致／パターン一致（パスの部分一致や末尾一致等）をサポートします。対象フィールドがレコードに存在しない場合、述語は「不一致」と評価されます。
- **空グループの削除**: フィルタリングの結果、`records`配列が空になった`thread`は`threads`から除外し、配下の`threads`配列が空になった`process`も`processes`から除外します。
- **タグの表現形式**: タグは各レコードの`tags`文字列配列に格納します。すでに`tags`を持つレコードへタグ付けを行う場合（例: `clew`パイプラインを多段実行する場合）は、既存のタグを保持したまま重複なくマージします。
- **ファイル内容に基づく種別判定**: `-tag-file-type`が有効な場合、`clew`は参照先のローカルファイル（利用可能であれば`resolved_path`、なければ`path`）について、ファイルヘッダ／マジックバイト検査や組み込みプリセット（および対応する場合は外部`file`コマンド連携等）を用いて種別を判定します。後処理時点で対象ファイルが存在しない、または読み取れない場合は、パイプラインを失敗させず該当レコードのファイル内容ベースのタグ付けをスキップします。

## グルーピング仕様と出力スキーマ

`pid,tid`でグルーピングする場合の仕様は以下のとおりです。

- レコードを`processes`（`pid`単位）→ `threads`（`tid`単位）→ `records`の2階層配列構造に整理します。
- キー付きマップではなく配列を採用することで、決定的な順序（例: `pid`昇順・`tid`昇順でソートし、各スレッド内のレコードは観測順を保持）を維持しやすく、将来プロセス単位やスレッド単位のメタデータフィールドを追加しやすい構造にします。
- 入力に含まれるトップレベルの完全性メタデータ（`lost`、`loss_breakdown`、`descendants_remaining`、`limitations`）をそのまま保持します。

出力構造の例:

```json
{
  "format": "ichnograph.clew.v1",
  "processes": [
    {
      "pid": 1234,
      "threads": [
        {
          "tid": 1234,
          "records": []
        }
      ]
    }
  ],
  "lost": 0,
  "loss_breakdown": {},
  "descendants_remaining": false,
  "limitations": []
}
```

## エラーハンドリングと制約

- 入力が有効なJSONでない場合や、指定された処理に必要な構造を満たさない場合は、標準エラー出力に明確なエラーを出力して終了ステータス`1`で終了し、`-o`指定先へ不完全な出力を書き込みません。
- `clew`による後処理は渡された入力データ（およびファイル種別タグ付け有効時は後処理時点で読み取り可能なローカルファイル）のみを対象とします。トレース中に失われたイベント（`lost` / `loss_breakdown`）を復元することはできないため、不完全な観測を完全な網羅と誤認させないよう`limitations`および欠損メタデータを引き続き出力に含めます。
- ファイル内容に基づく種別判定は`clew`実行時点のローカルファイル状態を反映するため、トレース収集時点の状態とは異なる場合があります。対象ファイルが存在しない・削除済み・読み取り不可の場合は致命的エラーとせずスキップします。
